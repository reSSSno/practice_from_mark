# Отчёт о реализации каталога

## Результаты измерений

Проверка проводилась 18.11.2026 в Opera на локальном сервере `http://127.0.0.1:8000`. В каталоге 50 000 товаров. Значения взяты из браузерных DevTools и результатов GitHub Actions. Отдельных измерений исходной версии приложения не проводилось.

| Показатель | Результат |
|---|---|
| Время поиска по запросу «клавиатура» | 61 мс в Web Worker при проверке офлайн |
| INP | 14 мс (запись Performance) |
| CLS | 0 (запись Performance) |
| Длинные задачи основного потока | Точное количество не подсчитано |
| Размер ответа `/api/items` | 595 140 байт (Content-Length при `Content-Encoding: gzip`), примерно 581 КиБ |
| Повторная загрузка по ETag | Заголовок ETag присутствует; получение 304 вручную не проверено |
| Валидация `limit=0` | API возвращает сообщение о нарушении ограничения `ge=1` (ожидаемый статус 422) |
| Автоматические тесты | Четыре теста pytest, GitHub Actions завершился успешно |
| Работа без сети | Страница и поиск работают при включённом Offline в DevTools |
| Обработка 404 и таймаута | Проверено вручную: сообщение об HTTP 404 и таймауте 5 секунд отображается корректно |

Число 595 140 байт относится к заголовку `Content-Length` конкретного сжатого ответа, а не к общему объёму ресурсов страницы. В офлайн-записи Network показано 0 Б переданных данных при загрузке из локального кеша; это не размер JSON.

## Выполненные проверки

1. **Поиск.** Запрос «клавиатура» возвращает подходящие карточки. Поиск выполняется в Web Worker; при офлайн-проверке интерфейс показал время 61 мс. Быстрая смена запросов проверена вручную, заметных проблем с отображением последних результатов не обнаружено.
2. **API.** Для `/api/items?limit=0` получен ответ с ошибкой валидации `greater_than_equal` и ограничением `ge: 1`. В ответе обычного запроса `/api/items` присутствуют `Content-Encoding: gzip` и ETag.
3. **Service Worker.** В Application → Service Workers отображается статус `activated and is running`. После переключения Network в Offline страница открылась, товары остались доступны и поиск продолжил работать.
4. **Производительность.** В записи Performance отображаются INP 14 мс и CLS 0. Отдельного подсчёта задач Main продолжительностью более 50 мс и сопоставимого замера первоначальной реализации нет.
5. **Обработка ошибок.** При временной замене API-адреса на `/api/nope` приложение показало сообщение «Не удалось загрузить каталог: сервер ответил 404». При запросе `/api/items?delay=8` показано сообщение «Сервер не ответил за 5 секунд. Попробуйте обновить страницу». Обе проверки подтверждены скриншотами.
6. **Тесты.** GitHub Actions с запуском pytest завершился успешно. В набор входят проверки схемы, валидации, ETag/304 и GZip.

## Реализация

- Семантическая разметка `header`, `main`, `search`, `label`, `ul/li`; статус загрузки и поиска через `role="status"` и `aria-live`.
- Карточки создаются через DOM API и `textContent`, без вставки названий товаров через `innerHTML`.
- Нечёткий поиск вынесен в Web Worker; идентификатор запроса позволяет не отображать устаревшие результаты.
- Загрузка каталога использует `fetch`, `AbortController`, ограничение ожидания в 5 секунд и проверку `response.ok`.
- FastAPI использует Pydantic-схему `Item`, ограничения параметров, GZip и ETag с поддержкой HTTP 304.
- Service Worker применяет cache-first к файлам интерфейса и network-first к API, сохраняя данные для офлайн-работы.

## Наблюдение

При отключённой сети поиск по уже загруженному каталогу продолжает работать. Это показывает, что вычисление результатов не зависит от постоянного подключения к API: после загрузки данных поиск выполняется локально в Web Worker. При этом по текущим замерам нельзя количественно оценить ускорение относительно первоначальной версии — для такого вывода нужны измерения обеих реализаций в одинаковых условиях.

## Что ещё проверить

- Получение HTTP 304 при запросе с `If-None-Match`.
- Размер ответа без GZip и количество длинных задач Main, если требуется численное сравнение «до/после».

## Технические решения

1. Вычисления длительностью 100–200 мс в основном потоке могут задерживать обработку ввода и отрисовку.
2. Web Worker выполняет поиск отдельно от основного потока интерфейса.
3. Номер запроса не позволяет более позднему ответу на старый поисковый запрос заменить актуальные результаты.
4. Массив из 50 000 товаров передаётся воркеру при загрузке каталога, а не при каждом вводе символа.
5. ETag зависит от версии каталога и значения `limit`, поскольку эти параметры определяют содержимое ответа.
6. `no-cache` допускает хранение ответа с повторной проверкой актуальности, а `no-store` запрещает его хранение.
7. `response_model` задаёт контракт API и проверяет структуру данных; затраты на валидацию следует учитывать при профилировании.
8. Cache-first подходит для оболочки приложения, а network-first позволяет сначала получать актуальные данные API и использовать кеш при недоступности сети.
