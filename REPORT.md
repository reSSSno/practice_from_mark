|---|---|---|
| Время одного поиска | Не измерено | Не измерено |

**Что сделано:** семантика header/main/search/label/ul/li и aria-live; поиск в Web Worker с фильтрацией устаревших ответов по id; AbortController + AbortSignal.timeout(5000) + AbortSignal.any; Pydantic и валидация параметров; GZip, ETag, 304; четыре теста pytest; Service Worker с cache-first для оболочки и network-first для API.

**Как получить реальные цифры:** в DevTools → Performance сравнить первоначальную реализацию поиска в основном потоке с текущим при вводе «клавиатура»: время поиска, число задач Main >50 мс и INP. В Network измерить Transferred для /api/items с отключённым и включённым GZip и повторным If-None-Match. В Application проверить shell-v1 и api-v1, затем включить Offline и обновить страницу. Заполнить таблицу измерениями; ориентиры из задания не являются измерениями.

**Наблюдение:** вычисления поиска могут занимать столько же времени, но пользователь не ощущает задержку, поскольку Web Worker освобождает главный поток.

## Технические решения
1. 100–200 мс — несколько кадров при бюджете ~16,7 мс на кадр, ввод начинает тормозить.
2. Worker выполняет вычисления вне Main; UI продолжает реагировать.
3. id не даёт позднему ответу для «кабе» заменить результат для «кабель».
4. structured clone массива из 50 000 объектов дорогой, поэтому передаём его один раз.
5. ETag включает limit, иначе разные ответы могли бы ошибочно считаться одинаковыми.
6. no-cache разрешает хранение с обязательной перепроверкой; no-store запрещает хранение.
7. response_model даёт контракт и валидацию, но проверка 50 000 объектов стоит времени: решение принимают по профилированию.
8. Cache-first для оболочки ускоряет загрузку и обеспечивает офлайн; network-first для данных сохраняет актуальность при наличии сети.
